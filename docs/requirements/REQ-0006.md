# REQ-0006：M2 单角色单副本真实业务闭环

状态：Ready for Codex  
优先级：P0  
依赖：REQ-0004、REQ-0005  
目标：**开始真实业务开发，不再继续扩建基础设施。**

## 1. 本轮目标

跑通第一条真正可用的业务链：

```text
当前角色
→ 进入副本入口
→ 识别目标副本
→ 打开副本详情
→ 确认“免费(1/1)”
→ 真正点击进入
→ 等待加载
→ 战斗
→ 识别胜利/失败
→ 处理奖励/返回
→ 写入 DailyExecution
```

本轮允许真实游戏点击。

先只做：

- 当前角色。
- 一个用户指定/实测可达副本。
- 一次完整闭环。
- 优先使用游戏原生自动战斗。

不要同时做多角色、多副本、复杂 Boss 技能策略。

## 2. 开发原则

从现在开始业务优先。

不再新增大规模框架、抽象层或“为了以后可能用”的防御机制。

只有以下最小安全条件必须保留：

1. 目标游戏 active。
2. WindowGate = MATCHED。
3. 当前页面已稳定识别。
4. 动作目标已识别。
5. 涉及副本次数时必须明确识别“免费(1/1)”。
6. 购买/钻石/额外次数按钮永不自动确认。
7. 每一步最多有限重试，失败就停，不死循环。

除此之外，优先跑通业务。

## 3. 首个真实 Action Executor

实现真正的 Action Executor：

```text
ActionIntent
→ ActionPolicy
→ ActionGuard
→ ALLOW
→ AccessibilityController.tap()
→ 等待页面变化
→ 验证 postcondition
```

要求：

- 所有真实点击仍从 Action Guard 进入。
- 不允许业务模块直接调用 tap/swipe。
- 只实现本轮需要的少量动作。

首批动作建议：

```text
OPEN_DUNGEON
SELECT_DUNGEON
START_DUNGEON_FREE
CONFIRM_REWARD_OR_RETURN
```

实际名称可按真实 UI 调整。

## 4. 不再要求“完美按钮框”

REQ-0005 已经证明 OCR boundingBox 可用。

本轮允许：

- OCR 文字 boundingBox 中心点击。
- 经人工确认的 template target。
- Accessibility node bounds。

优先使用最稳定的一种。

不要因为“按钮框还不够完美”继续停留在基础设施阶段。

## 5. 副本页面采样

Codex 使用无线 ADB 配合用户手动操作，采集以下真实页面：

1. 副本入口/列表。
2. 目标副本卡片。
3. 副本详情。
4. “免费(1/1)”状态。
5. 进入/前往按钮。
6. 加载页。
7. 战斗页。
8. 胜利页。
9. 失败页。
10. 奖励/返回页。

若某页面无法一次采齐，边做边补。

不要等待“所有页面素材齐全”才开始写业务。

## 6. 目标副本

本轮只配置一个副本：

```text
targetDungeonId
targetDungeonName
```

具体名称以真机实测为准，不猜。

配置保存在本机或普通配置文件中。

## 7. 业务状态机

只增加当前业务必须的状态：

```text
DUNGEON_NAVIGATE
DUNGEON_SELECT
DUNGEON_DETAIL
FREE_CHECK
DUNGEON_START
DUNGEON_LOADING
BATTLE
RESULT_CHECK
REWARD
RETURN
SUCCESS
FAILED
```

不要求一次重构整个总状态机。

## 8. 免费次数规则

这是本轮唯一必须严格保留的业务保护。

只有同时满足：

```text
DailyExecution 今日未 SUCCESS
+
当前稳定页 = DUNGEON_DETAIL
+
FreeAttemptState = AVAILABLE
+
未检测到购买/钻石/额外次数确认
+
开始按钮目标已确认
```

才允许执行：

```text
START_DUNGEON_FREE
```

任何一个条件 UNKNOWN：

```text
停止该副本流程
→ 记录原因
→ 不点击
```

本轮不要求识别所有“免费已用完”的 UI 变体。

看不到明确免费状态就不进。

## 9. 原生自动战斗优先

本轮不做脚本技能释放。

进入战斗后：

1. 检测是否已经开启游戏原生自动战斗。
2. 如果需要点击一次“自动”，允许增加一个真实动作。
3. 然后等待战斗结果。
4. 每隔合理时间检查一次：
   - 胜利。
   - 失败。
   - 仍在战斗。
   - 异常/未知。

不要对技能栏逐技能操作。

## 10. 战斗超时

设置一个可配置战斗超时，例如：

```text
5~15 分钟
```

具体默认值由 Codex根据实测给建议。

超时：

```text
FAILED / TIMEOUT
→ 停止本次流程
→ 不继续乱点
```

## 11. 结果识别

至少识别：

```text
VICTORY
FAILURE
UNKNOWN
```

胜利后：

- 处理奖励页或返回。
- 验证已回到安全页面。
- 写 DailyExecution SUCCESS。

失败：

- 写 FAILED。
- 本轮默认不自动重打。
- 停止流程。

UNKNOWN：

- 等待有限时间。
- 超时后失败退出。

## 12. DailyExecution

成功条件必须是：

```text
副本已完成
+
结果已确认
+
流程已安全返回
```

不能在“点击进入副本”时提前写 SUCCESS。

建议状态：

```text
PENDING
RUNNING
SUCCESS
FAILED
```

记录：

- gameDayKey
- roleId/currentRoleKey
- dungeonId
- startedAt
- completedAt
- result
- errorCode

本轮 currentRoleKey 可以先用本机配置，不需要马上完成角色识别系统。

## 13. UI

主页增加最小业务区：

- 当前目标副本。
- 当前业务状态。
- “运行一次单副本测试”按钮。
- 当前页面。
- 免费状态。
- 最近一步动作。
- 最近错误。
- 成功/失败结果。

不做复杂配置中心。

## 14. 真实点击日志

每个动作记录：

```text
timestamp
actionType
pageBefore
targetRect
guardDecision
tapResult
pageAfter
duration
```

不要记录截图 bytes。

## 15. 重试

每个业务步骤默认：

```text
maxRetries = 2
```

不要无限重试。

重试前必须重新识别页面。

## 16. 本轮不做

明确禁止扩展到：

- 多角色轮询。
- 多副本调度。
- 自动角色切换。
- 日常任务。
- 手动技能策略。
- Boss 技能识别。
- 云端 AI。
- 复杂自动恢复框架。
- 新一轮大规模“安全架构重构”。

这些都等单副本闭环跑通再做。

## 17. 验收标准

只有以下内容是本轮核心验收：

1. APK 真机可运行。
2. 用户点“运行一次单副本测试”。
3. 系统从当前角色开始。
4. 自动进入目标副本。
5. 真正识别“免费(1/1)”。
6. 真正点击进入副本。
7. 战斗采用原生自动。
8. 能识别胜利或失败。
9. 胜利后完成返回/奖励处理。
10. DailyExecution 写入正确结果。
11. 同日再次运行时不会再次消耗同一副本免费次数。
12. 未确认免费状态时绝不进入。
13. 未发生任何购买/钻石/额外次数确认。
14. 失败后不会无限乱点。
15. 完整流程至少真机成功跑通 1 次。
