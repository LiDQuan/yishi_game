# REQ-0004：M0 Android 基础设施与 Pad 环境采集

状态：Ready for Codex  
优先级：P0  
依赖：REQ-0003

这是 Codex 当前应立即开始实施的第一个业务开发任务。

## 1. 目标

建立后续自动化所需的稳定基础，不实现真实刷副本。

完成后必须具备：

- 可构建、可安装、可启动的 Android APK。
- 中文平板 GUI 壳。
- AccessibilityService 基础服务。
- 屏幕捕获基础能力。
- Room 数据库骨架。
- 自动化状态机骨架。
- 安全停止机制。
- ADB Pad Inspector。
- 对目标 Pad 的设备/窗口采样报告。
- 初步游戏窗口检测与标准化可行性结论。

## 2. Android 工程

建议使用：

- Kotlin
- Jetpack Compose
- 单 Activity
- Coroutines / Flow
- Room

不要为了“未来可能用到”过早引入大量框架。

工程必须：

- 可以在本地通过标准 Gradle 命令构建 debug APK。
- 能通过 ADB 安装到已连接 Pad。
- 包名、minSdk、targetSdk 和依赖版本记录在 IMPLEMENT 报告。
- 不在仓库提交 `local.properties`。

## 3. MVP GUI

首页至少包含：

- 应用名称。
- 当前状态。
- Accessibility 权限状态。
- 屏幕采集状态。
- 目标游戏检测状态。
- 当前设备摘要（脱敏）。
- “环境检查”按钮。
- “开始自动化”按钮：M0 阶段保持禁用，直到基础前置通过。
- “停止”按钮。
- “查看诊断”入口。

M0 不追求最终视觉设计，但应适合平板大屏，避免仅按手机窄屏布局。

## 4. AccessibilityService

建立正式服务类与控制层。

M0 要求：

- 能检测服务是否已启用。
- 能打开系统辅助功能设置页。
- 提供统一接口骨架：tap / swipe / back / queryWindows。
- 业务层不得直接依赖具体 AccessibilityService 实现。
- 所有后续点击必须预留接入 Action Guard。

M0 不执行真实游戏自动点击。

## 5. 屏幕捕获

建立屏幕捕获抽象。

要求：

- 支持 MediaProjection 授权流程。
- 能获取一帧当前屏幕或目标内容截图供后续识别使用。
- 正确处理用户拒绝授权。
- App 退出/服务销毁时释放资源。
- 原始截图默认不写公开仓库。

具体持续采集服务形态由 Codex按 Android 当前平台限制实现并在报告中解释。

## 6. Pad Inspector

实现 `tools/pad-inspector/`。

目标：Mac 通过已打通的无线 ADB 一次性采集目标 Pad 的开发信息。

至少收集：

- 设备制造商/型号。
- Android 版本。
- 构建信息中必要的非敏感字段。
- `wm size`。
- `wm density`。
- 屏幕方向。
- 当前 resumed activity / foreground package。
- `dumpsys window` 中与当前窗口和目标游戏相关的必要片段。
- UIAutomator dump（若可用）。
- 当前截图：默认保存本地私有目录，不提交公开仓库。

建议命令：

```bash
python3 tools/pad-inspector/pad_inspector.py capture
```

输出：

```text
~/.config/yishijieyongzhe/private/pad-reports/<timestamp>/
├── device.json
├── display.json
├── foreground.json
├── window.txt
├── ui.xml
└── screenshot.png
```

另外生成一个可公开的脱敏摘要：

```text
diagnostics/device-sample.example.json
```

仅包含非敏感示例/结构，不包含真实序列号、IP、ADB endpoint 或用户路径。

## 7. 目标游戏识别

不要把尚未确认的包名写死。

Pad Inspector 应能在用户把游戏置前台时发现 foreground package，并提示 Codex把确认后的包名放入本地设备配置。

公开仓库只保留示例：

```text
TARGET_GAME_PACKAGE=
```

## 8. 游戏窗口检测原型

本任务必须调查并记录联想电脑模式下：

- `dumpsys window` 是否能给出目标游戏 bounds。
- 是否能区分窗口外框与游戏内容区。
- 窗口移动/缩放后系统信息如何变化。
- Accessibility 窗口信息能否获得稳定 bounds。
- 通过 Accessibility 操作系统窗口边框进行 resize 是否可行。

至少进行三组样本：

1. 标准窗口。
2. 人工缩小窗口。
3. 人工移动窗口。

输出结论到：

`codex/reports/IMPLEMENT-0004.md`

如果自动 resize 在该 ZUI 版本不可行：

- 不视为任务失败。
- 必须证明“检测变化 → 阻止自动化”可以可靠实现。
- 给出下一任务的替代方案。

## 9. 状态机骨架

M0 实现以下状态即可：

```text
IDLE
PRECHECK
PERMISSION_REQUIRED
DEVICE_READY
WINDOW_CHECK
READY
RUNNING_PLACEHOLDER
PAUSED
ERROR
STOPPED
```

必须保证：

- 非 READY 不能进入真实自动化。
- STOP 可从任何运行态安全进入 STOPPED。
- ERROR 不继续自动点击。
- 状态变化可观察并记录。

## 10. Room 数据库骨架

创建 schema 和 DAO 骨架，至少包含：

- Role
- Dungeon
- DailyExecution
- ErrorEvent
- AppSettings

字段遵循 `docs/architecture/data-model.md`。

M0 只需 CRUD/基本测试，不需要录入真实角色。

## 11. 诊断日志

使用结构化事件，而不是只打印自然语言。

至少包含：

- timestamp
- eventType
- state
- result
- errorCode
- metadata（禁止 Secret）

Logcat 可以保留开发日志；公开报告只能脱敏。

Codex必须实际执行并记录：

- 配置解析测试。

## 15. 验收标准

满足以下全部条件才算完成：

- debug APK 构建成功。
- APK 在目标 Pad 安装并启动成功。
- 权限状态可正确展示。
- MediaProjection 至少成功抓到一帧。
- Pad Inspector 能生成完整本地报告。
- foreground game package 可被识别。
- 三组自由窗口采样完成。
- 可判断窗口是否发生变化。
- 自动 resize 可行性有实测结论。
- STOP / ERROR 状态不会继续执行点击。
- Room 骨架测试通过。
- 安全扫描通过。
- IMPLEMENT-0004 内容足以让 ChatGPT复审。
